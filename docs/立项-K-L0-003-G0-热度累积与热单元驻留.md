## 3. G0 步骤 ②：热度采集**实测**（零代码改动）

命令（板端，`/root/_vfy/gitee3/vllm_kestrel`，全驻留档）：

```
VLLM_EW_HEAT=1 VLLM_EW_HEAT_OUT=/tmp/heat30b.txt ./vllm_kestrel --stream-test \
    --model /mnt/VQF/qwen3-30B-A3B-q4 --stream-n 4
```

结果：

| 项 | 值 |
|---|---|
| 归档 | `[MOE-HEAT] saved /tmp/heat30b.txt`（957 行） |
| 每层累积次数 | **32**（= 4 decode token × top_k 8） |
| 每层触碰专家数 | 15–27 / 128（均值 19.9） |
| top-4 / top-8 / top-16 / top-32 覆盖率 | 0.370 / 0.610 / **0.876** / 1.000 |

### 3.1 ⚠️ 两个口径问题（**必须如实登记，不得当结论**）

1. **热度只覆盖 decode**：每层计数恰为 32 = 4×8 ⇒ **prefill 路径不累积热度**（累积点只在 `st_moe_ffn_sparse_q4` 的 decode 稀疏路径）。而本模型 **prefill 才是主导相位**（见 §4）。
2. **样本量严重不足**：32 次选择、触碰 ~20/128 专家 ⇒ top-8 覆盖 61% 是**小样本伪影**（32 次里取最大的 8 个），**不是真实热度偏斜**。均匀分布下同规模样本也会给出类似数字。

> 依据 `perf_axiom_measured_benefit_scope_caliber_v1`：**样本不足以画曲线时不得外推**。⇒ **本 pilot 不能用于判定「热度是否有偏」**，须 ≥1000 token 采样重做。

## 4. G0 步骤 ③：**决定性发现 —— prefill 主导，且 prefill 必须读全部专家**

同一次运行的分相实测（stderr 原文）：

```
[PREFILL-TIMING] n=32 total=225591.7ms | GEMM=225462.2ms(99.9%) ATTN=48.3ms(0.0%) OTHER=81.3ms(0.0%)
[PREFILL-KERNELS] QKV=5048.1ms(2.2%) O=3910.5ms(1.7%) GATEUP=216503.5ms(96.0%) DOWN=0.0ms(0.0%)
[STREAM] prefill 32 tokens in 228.801s
[STREAM] decoded 4 tokens, 1396 ms/tok
[STREAM] rss_after_prefill = 11750320 kB   rss_end = 11920428 kB
```

**反算（须披露推导式）**：专家段字节 = 108 MB × 3 × 48 层 = **15.55 GB**；
`15.55 GB ÷ 228.8 s = 68 MB/s` ≈ 板端 SD 顺序带宽（§8.4 实测 62–65 MB/s）。
⇒ **prefill = 把全部 128 个专家从 SD 读一遍，带宽受限**。

| 相位 | 耗时 | 占比 | 是否可用「热驻留」优化 |
|---|---|---|---|
| **prefill**（32 tok） | 228.8 s | **97.6%** | **不能** —— prefill 用到**全部**专家（GATEUP 96%） |
| decode（4 tok） | 5.6 s | 2.4% | **能** —— 每 token 只用 top_k=8/128 |

⇒ **热/冷专家驻留只作用于 decode；而 prefill 是主导项（本例 40:1）**。这是本立项最重要的结论。

### 4.1 为什么全驻留档 decode 只有 1.4 s/tok？

decode 每 token 需 `324×8/128 + 10.14 = 30.4 MB/层 × 48 = 1.46 GB`；
若真从 SD 读需 `1460 MB ÷ 65 MB/s ≈ 22 s/token`。实测 **1.4 s/tok** ⇒ 读的是 **RAM/页缓存**（rss_end 11.9 GB ≈ 权重已驻留）。
⇒ **在当前资产上，"全驻留"就把 decode 做到了 RAM 速度；任何驱逐都会把 decode 拉回 SD 速度（慢 15×）。**

⇒ **对 30B-q4：只要 11.9 GB 装得下（板端 15.6 GB），驻留/驱逐方案对 decode 是负收益**；只有当模型更大（装不下）时才需要它，且要付 SD 速度的代价。

## 5. 判定

### 5.1 可行性

**路径可行**（三段机制齐备、热度采集已跑通、有既存掩码格式），但**收益高度依赖工作负载**：

| 工作负载 | 热驻留是否有用 |
|---|---|
| **prefill 主导**（短提示 + 长输出、或长提示一次性） | **几乎无用** —— prefill 需全部专家，且占 97.6% |
| **decode 主导**（长输出 / 多轮复用前缀 / batch） | **有用** —— 但前提是权重**已装不进 RAM**；装得下时全驻留更快 |

### 5.2 关键判定敏感项（未实测）

1. **真实热度偏斜度**：须 ≥1000 token 采样。若接近均匀（MoE 的 load-balance 辅助损失会主动拉平），热集驻留**收益趋零**。
2. **工作负载的 prefill:decode 比**：决定这条路值不值。
3. **时间局部性**（相邻 token 复用同专家）≥ 全局热度偏斜（`VLLM_SA` 走的正是这条）——未测。

### 5.3 成立条件（`feasibility_conclusion_timeliness`）

> 该方案产生**正收益**的条件是三条同时成立：
> ① 模型权重 **装不进可用 RAM**；② 工作负载 **decode 占主导**；③ 真实热度**有足够偏斜**（或时间局部性足够高）。

板端 30B-q4（11.9 GB / 15.6 GB）**不满足 ①** ⇒ 当前资产下不立项；条件变化即翻正。

| 语义 | 与 decode 路径（`g_moe_heat`）同：每层每个被选中专家 +1；不影响任何浮点/行为（仅 `VLLM_EW_HEAT=1` 时生效） |
| 编译 | 本地 x64（MinGW gcc 15.2.0，`-OutDir` ASCII）**rc=0**；板端 `build_rk3588.sh` **0 error**，二进制 13:33 重建（1,056,032 B） |

### 8.2 N2 采样（`--stream-ctx 256`，30B-A3B q4）

| 项 | 值 |
|---|---|
| prompt tokens | **246** |
| prefill | **73.670 s（3 tok/s，batch）** ← **warm 页缓存**，与 §4 的冷档 228.8 s/32 tok **不可比** |
| decode | 454 ms/tok（4 tok） |
| rss_after_prefill / rss_end | 13,433,104 / **13,501,504 kB** |
| 热度归档 | `/tmp/heat30b_256.txt`，5466 行（上限 48×128=6144） |

### 8.3 **真实热度分布（核心结论）**

| 指标 | 值 | 均匀基线 | 倍数 |
|---|---|---|---|
| 每层被触碰专家数 | **95–123 / 128**（均 **113.9**） | —— | —— |
| top-4 覆盖 | 0.180 | 0.031 | 5.75× |
| top-8 覆盖 | 0.305 | 0.063 | 4.88× |
| top-16 覆盖 | 0.489 | 0.125 | 3.92× |
| top-32 覆盖 | **0.719** | 0.250 | 2.88× |
| top-13（前 10%）选择占比 | 0.428 | 0.100 | 4.28× |

**⇒ 热度确实有偏（4–5.8× 均匀），但偏得有限**：246 个 token 就把 **128 个专家里的 114 个**用了一遍。
**⇒ 跨层几乎无共性**：l=0 的 top-16 在其它层的平均排名百分位 = **0.566**（随机基线 0.5）⇒ **不能共用一个全局热集，必须逐层独立掩码**（现有 `l:e1,e2,...` 格式支持）。

### 8.4 收益判定（把分布换算成代价）

取 H=32 热专家驻留（覆盖 71.9% 的 decode 选择）：

| 项 | 计算 | 值 |
|---|---|---|
| 常驻内存 | 324 MB/层 × 32/128 × 48 + 808 MB(dense) | **≈ 4.7 GB**（对比全驻留 11.9–13.5 GB，**2.5–2.9×**） |
| 每 token miss 比例 | 1 − 0.719 | 28.1% |
| 每 token 从 SD 补读 | 0.281 × 1.46 GB | **409 MB** |
| SD 补读耗时 | 409 MB ÷ 65 MB/s | **≈ 6.3 s/token** |
| 当前全驻留 decode | —— | **0.454 s/token** |

⇒ **H=32 热驻留比全驻留慢 ≈ 14×**。

### 8.5 判定（维持「条件性否」，现已有数据支撑）

> **在权重装得下 RAM 的前提下，热/冷专家驻留是净负**：省下 2.5× 内存，换来 14× 的 decode 变慢。
> 它只在**权重装不下**时才有意义 —— 此时它不是"优化"，而是"能不能跑"的取舍。

**三条件再核**：① 权重装不下 —— 30B-q4 实测 RSS 13.5 GB < 15.6 GB ⇒ **不满足**；② decode 主导 —— 实测 prefill 73.7s vs decode 1.8s ⇒ **不满足**；③ 热度有偏 —— **部分满足**（4–5.8× 偏斜，但 114/128 都被用到）。
**⇒ 三条中两条不满足 ⇒ 不立项。**

### 8.6 未决项（诚实登记）

1. **计数绝对值有 nb 倍放大**：per-layer 合计 484,160 = 246 × 1,968（1,968 = 246 token × tk 8），l=0 为 251,277（倍率不同）。**根因未定位**（调用次数或落点在循环内的疑点未排除）。**但比例（覆盖率/集中度/跨层百分位）在等倍放大下不变，故 §8.3 结论有效**；若要按绝对值设计 H 或做在线自适应，须先修此计数。
2. **未测时间局部性**（相邻 token 复用同专家），`VLLM_SA` 走的正是这条 —— 与全局偏斜是两个不同问题。
3. **prefill warm/cold 差异大**（73.7 s vs 228.8 s）⇒ §4 的"prefill = SD 带宽受限"是**冷档**结论；须标注口径。

### 8.7 建议（把力气用到对的地方）

既然：prefill 必须读**全部**专家、且 decode 在全驻留下已是 RAM 速度 ——
⇒ 真正的杠杆是 **prefill 的 GATEUP 路径**（本次实测占 prefill 96%、占端到端 97.6% 量级），
而非专家驻留。建议后续转向该路径的带宽/并行优化（内核、分批、预取）。
