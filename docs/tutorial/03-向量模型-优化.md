# 03 · 向量模型 · 优化篇：先判别瓶颈，再承认地板

> 系列教程 · 第 3 篇 ｜ [返回总览](01-总览.md) ｜ 上一篇：[02 适配](02-向量模型-适配.md)
> 真源：[K-EMB-002](../立项-K-EMB-002-G0-向量模型prefill性能优化.md)

这一篇的主题不是「我优化了多少」，而是「**如何用数据判定『没有更多可优化空间』**」。它的最终结论是：收益仅 **−1.2%**。但它同时演示了整套瓶颈判别方法。

---

## 1. 原理：嵌入为什么没有「位置剪枝」的便宜可占

生成式 LLM 有很多「只算一部分」的技巧（KV cache、投机解码、稀疏注意力）。嵌入模型看起来也只需要**最后一个位置**的输出，直觉上应该能跳过大量计算。

**但这个直觉是错的。** 因果解码器的每一层都需要**全位置**的隐状态：

```
第 L 层第 n-1 位输出 = f( h_L[n-1], {K_L[j], V_L[j] | j ≤ n-1} )
而 {K_L[j], V_L[j]} = proj( h_{L-1}[j] )   ← 需要上一层所有位置
⇒ 要算末位，就必须算每一层的每一个位置
```

⇒ **嵌入的优化面只在 prefill 内核与并行度**，没有算法级剪枝。这是先冻结论，避免在错误的方向上投入。

## 2. 第一步：把时间切成相位（数据先行）

给 prefill 加 env 门控的分相计时（`VLLM_DEC_PROF=1`，默认关零开销），得到 521-token 文本的剖面：

| 相位 | 耗时 | 占比 |
|---|---|---|
| **GEMM** | 2161.6 ms | **73.6%** |
| ├ GATEUP（FFN 双投影） | 802.7 ms | 37.1% of GEMM |
| ├ QKV | 645.3 ms | 29.9% |
| ├ DOWN | 433.8 ms | 20.1% |
| └ O | 279.7 ms | 12.9% |
| **ATTN** | 560.4 ms | **19.1%** |
| OTHER（norm/MRoPE/KV-store/SiLU） | 215.5 ms | 7.3% |
| **合计** | **2937.5 ms** | 5.6 ms/tok |

两个**伸缩实验**进一步缩小范围：

| 实验 | 读数 | 判读 |
|---|---|---|
| `--prefill-batch` 64/128/256/512/1024 | 2.911/2.890/2.881/2.888/2.895 s **恒定** | 与顶层 mini-batch **无关** ⇒ 排除「顶层分块重读」 |
| OMP 1/2/3/4 | 10.007/5.176/3.940/2.890 s = **3.46×** | 第 4 核边际仅 ~1.06× |

## 3. 第二步：判别「带宽受限」还是「算力受限」

### 3.1 先算一个反算（会误导你，但必须写下来）

- GEMM MAC = 15.73 M/tok/layer × 28 层 × 521 tok = **229.4 G-MAC**；÷ 2.162 s = **106 GMAC/s**
- Q8 权重（不含 embed）~468 MB；若内层 token tile = 8 ⇒ 重读 65× ⇒ **等效 14.1 GB/s**

看起来「14.1 GB/s ≈ DRAM 屋顶」⇒ 会得出「**H1：权重带宽受限**」。**但这是算术巧合**。正确做法是做判别实验。

### 3.2 判别实验 A：纯读探针

给 Q8 GEMM 的 tile worker 加一个 env 门控分支（`VLLM_Q8_PROBE=1`，默认关）：**只按与真 GEMM 相同的访问模式读权重/激活字节**（每 64B 取 1 字节 ⇒ 触发整条 cache line 取回），跳过全部 `vdot`/累加/存储，累加进 `volatile` sink 防 DCE。

```c
if (g_probe) {                       // 纯读地板
    uint64_t s = 0;
    const size_t grp_bytes = (size_t)c->nb * 272;      // 每 8 行组的权重字节
    const int ngrp = (c->rows + 7) / 8;
    for (int g = 0; g < ngrp; g++) {
        const uint8_t *p = c->q8_w + (size_t)g * grp_bytes;
        for (size_t i = 0; i < grp_bytes; i += 64) s += p[i];
    }
    for (size_t i = 0; i < grp_bytes; i += 64) s += act[i];
    g_q8_probe_sink = s; return;      // 已 volatile，不会被优化掉
}
```

### 3.3 判别实验 B：DRAM 屋顶标定

写一个 20 行微基准（`/root/bw.c`）测 4×A76 的**顺序读带宽屋顶**：

| 形态 | 1 线程 | **4 线程** |
|---|---|---|
| stride64（1 字节/64B） | 21.76 GB/s | **27.05 GB/s** |
| stride16 | 18.30 GB/s | 27.54 GB/s |

⇒ 这块板子的 DRAM 屋顶 **~27 GB/s**。

### 3.4 判别结论

| 档 | GEMM | QKV | O | GATEUP | DOWN |
|---|---|---|---|---|---|
| 默认（真 GEMM） | **2046 / 2052 ms** | 522 | 281 | 806 | 436 |
| 纯读地板 | **804 / 806 ms** | 194 | 125 | 297 | 188 |

- **计算占比 = (2049 − 804)/2049 = 60.8%**，四个投影一致（55–63%）⇒ 是**内层固有**属性。
- **H1 证否**：同访问模式纯读只需 **39%** 的时间。若带宽受限，两者应等时。
- **H2 成立**：GEMM 有效 28 GMAC/s/核，仅 `vdotq` 微基准单核（93.6 GMAC/s）的 **30%**；且既非带宽也非 load-issue 受限（1.07 Gload/s ≪ A76 发射能力）⇒ 卡在**内层 f16-scale 反量化 + `vdotq_laneq` 调度**。
- **订正**：§3.1 的「14.1 GB/s≈屋顶」是算术巧合（把 GEMM 时间当作带宽受限的前提错了）。

> **教学点**：这正是 `bottleneck_scaling_attribution` 的价值——**探针推翻了口算**。如果不做判别就直接按「带宽受限」去优化（比如降精度减字节），会一无所获。

## 4. 第三步：两条 GEMM 杠杆都撞墙

### 4.1 杠杆 A：加大 token 分块（被寄存器锁死）

8x8 GEMM 内核的形态是 **8 输出行 × 8 token**，寄存器占用：

```
16 个 int32 累加器 (acc00..acc17  → 8 行 × 8 token)
+ 16 个 f32 累加器  (sumf[2][8])
= 32 个 128-bit 向量 = AArch64 SIMD 寄存器文件的全部
```

加到 16 token ⇒ 需 64 个 ⇒ **必溢出**。这与本项目在 A76 上反复撞到的同一堵墙：

- K-PF-005 §9.4：ARM k-方向 ILP 镜像**无收益**（exact 轨 0%、actq 轨 +24%）；
- K-YOLO-002：8-way ILP **+3.7% 退化**；
- K-LAYA-002 M2b：16 个 NEON 累加器 **−27%**。

**tile-16 的既有实现**是 4x4 轨（4 行 × 16 token，仅 16 寄存器），但需要 **4x4 布局的 VQF**（当前 emb 模型是 8x8 `file=0x3`），env 切换会被 `vqf_load` 布局校验直接拒绝：

```
[VQF] layout mismatch: file=0x3 engine=0x2
```

⇒ 想拿 tile-16 得重转模型（板端无 HF 源/转换器）—— 成本高于预期收益。

### 4.2 杠杆 B：内层计算效率（被先例劝退）

61% 的 compute 若能压下来当然最好，但 K-PF-005 已实测「加宽 ILP 在 A76 上无效」，须换结构（寄存器/调度/反量化融合）——属高风险深内核工作。

## 5. 第四步：转向「删无用工作」——Phase 2

既然 GEMM 不好动，就看**整体里哪些工作对嵌入是纯浪费**。嵌入**无 decode**，所以以下三件只为 decode 服务的事可以删：

| 项 | 为什么是浪费 | 删法 |
|---|---|---|
| **imp_head 注意力质量图** | 只给稀疏 decode 选块用；内层 O(n²·nh) 累加 | 注意力 3 个调用点传 `NULL` + 末尾归约跳过 |
| **末尾 LM head logits** | 嵌入不产 token，logits 无人用 | 门控跳过 matvec（`normed_b` 仍照算） |
| **KV int8 压缩包** | 仅 int8 注意力/nof32 正典需要 | guard：`!g_kv_nof32 && !st_attn_i8_enabled()` 才跳 |

关键是**门控条件限定 embedding**：

```c
int emb_skip = 0;
if (g_embed_out) {                    // 只有登记了取值钩子才生效
    static int g_esw = -1;
    if (g_esw < 0) { const char *e = getenv("VLLM_EMB_SKIP_WASTE");
                     g_esw = (e && e[0]=='0') ? 0 : 1; }   // 默认 1，=0 逃生舱
    emb_skip = g_esw;
}
```

⇒ 触发条件限 `g_embed_out != NULL`（仅嵌入路径）⇒ **对 chat 路径构造上零影响**。

> 有意思的是：KV q8 那一项**没跳成功**（`kvq8=0`）——因为这个模型走 **nof32 正典**（q8 就是正典），guard **正确拦住了**。这说明「删无用工作」的难点不在删，而在**判准哪些真无用**。

### 5.1 实测（521 tok，t4@A76，交错 3 轮）

| 轮 | 默认 | skip | Δ |
|---|---|---|---|
| 1 | 2879 ms | **2848 ms** | −1.1% |
| 2 | 2890 ms | **2854 ms** | −1.2% |
| 3 | 2897 ms | **2859 ms** | −1.3% |

- **J-EMB-1 位级 PASS**：向量 **3/3 轮逐位一致**（`[EMB-VEC]` 全等）——符合预期（attention 走 f32 正典、imp_head/logits 仅 decode 用）。
- G4 默认化前复核四条件：位级门 ✓ / 效应门（−1.7%）✓ / 逃生舱（`=0` 时凭证打印 0 次，不静默）✓ / chat 零影响（`--stream-test` 正常）✓。

## 6. 结论：判定「达该平台实际地板」

| 相位 | 占比 | 状态 |
|---|---|---|
| GEMM | 74% | H2 compute·issue 受限；ILP 加宽（先例证否）与 token 分块（寄存器锁死）**两杠杆均不通** |
| ATTN | 19% | 实测 55 GMAC/s ≈ **F32 屋顶的 72%**，近上限 |
| OTHER | 7% | 含 KV 正典写（必需）+ norm/mrope，可删项已删完 |

⇒ 最终收益 **−1.2%**，与 K-DENSE-015「稠密模型计算侧无空间」同结论。
